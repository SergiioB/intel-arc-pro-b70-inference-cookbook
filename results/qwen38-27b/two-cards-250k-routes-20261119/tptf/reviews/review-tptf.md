## Notes on code correctness

1. **The shared-tree bound holds for every valid row.** `zig/src/xpu/runner_multi.zig:20` limits the entire round to 16 rows and forbids duplicate slots. Its parent validation at line 50 then bounds each row's depth by its index within that window, at most 15. For a root at `p`, the position is `p + depth`. A nonempty prefix has exclusive end `pref_base(pos) <= pos - 16 <= p - 1`. An empty prefix reads nothing, including at root position zero. Each stream's speculative writes start at its own root, and the prefix kernels use the row's own K/V pointers. The tail maps keys at or after the root through the ancestor table. See `zig/kernels/xpu/qwen27/glue_attn.cl:70`, `decode.cl:77`, `decode.cl:93` and `:115`, and `decode_prefix.cl:11` and `:82`.
2. **Bug B fits its scratch buffers and preserves the prefix-off dispatch.** `zig/src/xpu/forward.zig:99` and `:421` size the buffers for at most 16 rows with rank-local head counts. `aq/akv` are 24/4, 12/2 and 6/1 at TP1, TP2 and TP4. Each prefix launch has `T` tiles in shared mode, `akv` K/V groups, six query heads per group and at most `npc` chunks. Both prefix kernels skip unused chunks per row and `attn_merge2` reads only those written. The tail covers the maximum of `PREMIN` and the chunk width plus the 16-position guard. A nonzero chunk launch implies context is large enough for that span, including unequal stream depths. With prefix off, `nch=0` keeps sliced attention. The source argument holds for bf16 and int8, and every supported TP degree. The measured shared-tree check covers bf16 TP2 only. See `zig/src/xpu/qwen27.zig:86`, `zig/src/xpu/forward.zig:425`, and `zig/kernels/xpu/qwen27/decode_prefix.cl:166`.
3. **The snapshot copy and ownership rules are consistent in the successful path.** `zig/src/xpu/slot_states.zig:23` through `:48` sizes GDN by `gv` and convolution by `nconv`. K/V uses `akv`, independent of `aq`. Each attention buffer holds K then V, with scales following the corresponding rows in int8 and no scales for bf16. The scale source or destination remains `MAX_CTX * kvr` into the slot buffer. Save and restore use the same offsets and rank-local list, and restore writes the selected slot's active convolution state, synchronizes, then the caller restores the drafter context. Save's error defer sees every pointer stored before a possibly failing copy. Normal eviction frees all populated entries after queue completion. A restore append failure can leave a partially restored slot, as before. Prefill handles the error by resetting and running cold on the ordered lists. A profiling-sync error can retain device memory until close, and the pre-existing `Gpu.free` drops ownership before checking whether the driver freed it. These paths matter more with 64 frees per rank. The store reserves and charges one rank's payload plus the rank-0 draft bytes, and evicts before save. `--prompt-cache-gib 0` disables the store. At TP2 the flag is a per-rank payload budget including the draft charge, with admission looking at rank 0, rather than a sum across both cards. The new format is in-process state. See `zig/src/xpu/slot_states.zig:53`, `:90` and `:124`, `zig/src/xpu/dev.zig:188`, `zig/src/xpu/ze.zig:442`, `zig/src/native/xpu_lanes.zig:208` and `:248`, and `zig/src/native/xpu.zig:118` and `:168`.

## Bug A root-cause tests, in priority order

### What the host code rules out

In the old code `zig/src/xpu/slot_states.zig:46`, the rank loop resets a local `usize` offset and uses `devAt(rk)` and `modelAt(rk)` together. The only rank-specific copy operands are the list and physical allocation pointers from the selected model. `select` binds every rank's active slot together. Its same-slot fast return relies on active pointers remaining bound. The failing cell has one stream, so a slot-switch error has little support. The source sizes depend on fixed runner shape and context, not stale per-rank counters. A stale active K/V pointer would explain a wrong **source**, but cannot by itself change the intended destination interval or write back at offset zero. The four length calculations and pointer offsets are `usize` through the Level Zero ABI. There is no `@truncate` or narrowing `@intCast` on this path. See old `slot_states.zig:57` and `:91`, `zig/src/xpu/runner_tree.zig:19`, `zig/src/xpu/qwen27.zig:328`, `zig/src/xpu/dev.zig:214`, and `zig/src/xpu/ze.zig:22`.

At 165,056 the old rank buffer holds 2,823,503,872 B. At the three tested 250K resume marks it holds 4,232,445,952 B, 4,242,030,592 B and 4,244,160,512 B, all below 2³². The TP2 int8 old buffer can exceed 2³² at 253,486 tokens, before grid alignment. At the 262,144-token sizing limit it is 4,439,048,192 B and the new largest layer is 272,629,760 B. These are allocation and cumulative offset sizes. Individual copies remain below 2³² even on the old path. The largest per-layer buffer across supported shapes at this context is 1 GiB, TP1 bf16. See `zig/src/xpu/limits.zig:5` and `zig/src/xpu/slot_states.zig:41`.

At 165,056, the intended layer-27 destination offsets are 1,063,624,704, 1,148,133,376, 1,149,453,824 and 1,233,962,496, with lengths 84,508,672, 1,320,448, 84,508,672 and 1,320,448 B. The first copy crosses the absolute 4 GiB boundary 8,019,968 bytes into that copy. The logged K and V ranges are disjoint from every intended snapshot destination. The two allocations come from `zeMemAllocDevice`, with no explicit host mapping or host staging in the save or restore. The trace itself uses host allocations for readback. There is no API-level overlap in the logged layer-27 ranges. An unexpected backing-memory alias or a runtime binding error remains possible. See `tptf/raw/a-arm-sources/code-160k/server.log:29`, `queue/logs/tptf-n-arm-sources.log:106`, and `zig/src/xpu/ze.zig:430`.

### Remaining explanations and decisive probes

1. **Most likely class: runtime address binding or command encoding depends on TensorFold's allocation and list state.** In the failing process, check after each of the four suspect appends. Record the list, source, destination, byte count, device, and allocation base and bounds for each. Hash the first 2 MiB and each intended destination, using an independent list or a device-side hash on an isolated repeat. Use distinct offset-coded data in the suspect source ranges if ordinary data cannot identify the writer. Correct API arguments and reproducible corruption limited to one list or command would localize the fault below the caller. Repeat that copy on a fresh ordered and then a regular list in the same context with the same pointers and explicit drains. A fresh standalone process changes too many variables. See probe `zig/src/xpu/slot_states.zig:82` and `alias/copy_alias.c:218`.
2. **Allocation placement, lifetime, or prior device work sets up the failure.** First run the same old fork binary at the failing fixture with only `XPU_ATTN_PREF=0`. That changes both execution and prefix scratch allocation sizes, so it is a discriminator. If it passes, reserve the same scratch while bypassing prefix execution, then vary allocation placement alone. Stamp and verify the *entire* live suspect regions and neighboring pages only in a throwaway snapshot. Compare clean pre-copy source bytes with the corrupt destination against all four source ranges, including scales, interior offsets and the 8,019,968-byte point. A fingerprint alone need not uniquely identify a write, so check the surrounding span. See `zig/src/xpu/forward.zig:77`, `:102` and probe `zig/src/xpu/cache_trace.zig:208`.
3. **Less likely: stale application state or a readback artifact.** Record all active pointers beside the intended slot's pointers, plus allocation IDs and ranges on each rank immediately before append. An independent host read of both the live recurrent source and snapshot at layers 26 and 27 would distinguish a changed live baseline from a changed snapshot. An immediate-list readback can itself perturb the submission sequence. Keep validation read-only and reserve a baseline before copying. A pointer mismatch proves an application-side bug, while disjoint verified regions and correct inputs eliminate the proposed stale-pointer/overlap path. Rank-0's bad result precedes rank-1 snapshot submissions, but the earlier TP workload is still present. See `zig/src/xpu/runner_tree.zig:19`, `zig/src/xpu/dev.zig:214` and probe `zig/src/xpu/cache_trace.zig:187`.

### Can the mitigation fail again?

Yes, if the failure follows absolute placement, queue/driver state, or pressure rather than large allocation length. A per-layer buffer can still cross an absolute 4 GiB address. The decisive regression is a read-only byte compare after save and after restore, plus greedy token hashes, while varying allocation placement and forcing multiple eviction and reallocation cycles. Cover the failing 165K and 250K coordinates first. Add a near-context-limit TP2 int8 point above the old 2³² size boundary, affordable TP1 and TP2 bf16 points, and a memory-feasible multi-slot replay with interleaved saves and cross-slot restores. Track actual driver memory, allocation failures, and eviction time. For Bug B, add a mixed-depth tree round spanning the first prefix boundary, with both int8 and bf16. See `zig/src/xpu/slot_states.zig:41`, `:67` and `:124`, and `zig/src/xpu/forward.zig:422`.
