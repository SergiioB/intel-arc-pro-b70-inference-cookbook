## 2. Source-verified draft-loop op inventory (pinned vLLM source)

`vllm/v1/spec_decode/llm_base_proposer.py`:

- `propose()` runs **one** step-0 forward of the MTP module over the batch, then calls
  `_sample_draft_tokens(sample_hidden_states, …)` — **LM-head application #1**.
- Then `for token_index in range(self.num_speculative_tokens - 1)` — for MTP4 that is
  3 more iterations, each running the MTP module again and calling
  `_sample_draft_tokens` — **LM-head applications #2–#4**.
- `_maybe_share_lm_head()` logs "Detected MTP model. Sharing target model lm_head weights
  with the draft model." — so all four applications read the **target's 2.543 GB F16 head**.

Per-token draft op list (matches `qwen3_5_mtp.py` `forward()`): `pre_fc_norm_embedding`,
`pre_fc_norm_hidden`, `cat`, `fc` (5120×10240), attention (q/k/v + q_norm/k_norm + RoPE +
KV write/read + o_proj), MLP (gate/up/SiLU/down), `post_attention_layernorm`,
`input_layernorm`, `norm`, then `compute_logits` (the full-vocab head) and the sampler.

## 3. The byte budget against the phase's 0.25 ms target

Per **spec step**, MTP4 (stock artifact, BF16 MTP + F16 head):

| Component | bytes / step | at 608 GB/s |
|---|---:|---:|
| 4 × MTP layer | 4 × 849.40 MB = 3 397 MB | 5.59 ms |
| 4 × LM head | 4 × 2542.80 MB = 10 171 MB | 16.73 ms |
| embedding gathers (rows only) | ~0.04 MB | ≈0 |
| **total draft-side weight reads** | **13.6 GB** | **22.3 ms** |

- The phase's budget: 0.25 ms/draft token allows **≈152 MB**. The measured requirement is
  **3 392 MB per draft token — 22.3× over budget.**
- Even a fully INT4 draft side (head 636 MB + MTP 212 MB ≈ 848 MB/pass) is **5.6× over**.
- The quarantined prototype's "1.5 ms per draft token" is **independently refuted by
  bytes**: 1.5 ms at 608 GB/s is 912 MB, less than the LM head alone (2 543 MB).
- **Stop rule applied: the phase mandates "Withdraw 0.25 ms if the byte budget disproves
  it." → withdrawn, with this arithmetic as the record.**

## 4. The pivot the phase anticipated

The phase's decision rule names this exact outcome: *"the byte inventory proving the LM head
dominates irreducibly (retarget to head reuse/caching work and record the pivot)."*

The head is **75 % of per-pass draft traffic** (2543 of 3392 MB) and 10.2 GB of the 13.6 GB
per step. It is re-read **once per draft token**, because MTP drafting is autoregressive
(draft *k+1* needs draft *k*'s token), so the four head applications cannot be batched.

Consequences, recorded as the retargeted scope:

1. The champion stack already attacks this: the recorded champion launch sets
   `B70_DRAFT_LMHEAD_INT4=1,B70_DRAFT_MTP_INT4=1` (draft-side INT4 patches). That is a
   **local patch**, not upstream — a cookbook/upstream candidate.
2. The remaining structural lever is **fewer head applications per step**, i.e. parallel
   (non-autoregressive) drafting, which reads the head once for K draft positions. Its
   ceiling here is ≈3 × 636 MB ≈ 1.9 GB → **≈3.1 ms/step** at INT4 — which lands inside the
   phase's own E0 range (~1.10×), unlike the withdrawn 0.25 ms target.
3. DFlash (the parallel drafter that already exists on this host) stays **closed** on this
   stack per RL-027/RL-028/RL-029 (selector NaN in eager, K-norm upstream bug, acceptance
   gap) — so the lever must be re-derived, not revived.

## 14. Audit-compliant re-run (calibrated p8192, measured-window acceptance) — and a new defect

Run: `PROMPT=8192 N=5` with the client's `--calibrate`, which sizes the prompt against the **server's
own tokenizer** (logged calibration: target 8,192 → **achieved 8,189**), and with acceptance computed
over the **measured window** (metrics snapshot before vs after the five samples) in addition to the
absolute counter. Evidence:
`results/2026/09/b70-improvement-probes-20260920/p4-champion-ab-p8192-n5-B70_DRAFT_LMHEAD_INT4_1_B70_DRAFT_MTP_INT4_1-20260921T114444Z/ (the T113616Z directory is an aborted n=0 attempt retained for the record)`.

| arm (n=5, 128/128 server-reported tokens) | post-first median | out-throughput median | acceptance (absolute) | acceptance (measured window) |
|---|---:|---:|---:|---:|
| champion (v5, no draft patch) | **55.61** | 18.20 | 0.5369 | 0.5676 |
| champion + draft INT4 pair | **80.32** | 20.33 | **0.6949** | **0.7027** |
| Δ | **+44.4 %** | +11.7 % | +0.158 | +0.135 |

**Two conclusions, one good and one bad.**

1. **The throughput effect reproduces for the third time and is now measured on a properly labelled
   cell**: +44.4 % here, +37.2 % (previous n=5) and +46.0 % (p512 n=3) — a consistent +37…+46 %
   band across three independent runs on the champion stack. The earlier cell-label defect is fixed
   (8,189 of 8,192 requested tokens).

2. **The patched arm's acceptance is NOT reproducible, and that is now the most important open
   defect.** Across runs of the *same* configuration the pair's acceptance measured 0.5529 and
   0.5547 in the earlier p8192/p512 runs, and **0.6949** here; the baseline arm stayed in a narrow
   0.53–0.58 band throughout. Because acceptance moved *in the patch's favour* by 0.13 in this run,
   the +44.4 % here is at least partly a **drafting-quality** effect, not purely the weight-traffic
   effect §11–§13 inferred. The mechanism claim must therefore be narrowed to: *draft-side INT4
   raises decode throughput by 37–46 %; the split between weight traffic and changed drafting
   behaviour is unresolved, and the acceptance of the patched configuration varies between runs*.

   A run-variable acceptance in the patch's own draft path is also a **correctness-shaped signal**,
   not merely a measurement nuisance: the two patches are local, env-gated, and touch the draft's
   LM head and MTP body. Nothing here shows wrong output — every emitted token is still
   target-verified — but a nondeterministic acceptance must be understood before this is upstreamed,
   added to a cookbook recipe, or quoted publicly.

**Status for P4:** the phase's E0 question is answered (a 1.37–1.46× lever exists and is reproducible
in magnitude), but the phase **cannot close** until the acceptance instability is attributed and the
claims audit's remaining fix list (greedy token-parity on the champion image, energy/temp telemetry,
the patch-generation provenance question) is worked. Recorded, not hidden.

## 15. Repeatability control: the throughput effect holds; the acceptance is the noisy part

Design: the champion harness with `BOTH=1`, i.e. **both arms patched identically**, so any arm-to-arm
difference is nondeterminism rather than the variable. Same cell (calibrated p8192, g128), n=5 per
arm, fresh container per arm. Evidence:
`results/2026/09/b70-improvement-probes-20260920/p4-champion-ab-p8192-n5-…-20260921T121436Z/`.

| arm (both = champion + draft pair) | post-first median | spread | acceptance (abs) | acceptance (window) |
|---|---:|---|---:|---:|
| A | **80.61** | 74.27–91.15 | 0.5906 | 0.6577 |
| B | **78.27** | 64.14–83.07 | 0.6194 | 0.5934 |

**Read this with the earlier runs to hand:**

| configuration | post-first medians across runs | acceptance (abs) across runs |
|---|---|---|
| champion baseline | 55.61, 52.99, 52.83, 42.76(local), 38.71(local) | 0.5335–0.5753 (narrow) |
| champion + draft pair | **80.61, 78.27**, 80.32, 72.68, 69.14(local), 77.14(p512) | **0.5529, 0.5547, 0.5906, 0.6194, 0.6949** (wide) |

Two conclusions, and they point in different directions from §14:

1. **The throughput effect is robust and is NOT an artifact of acceptance luck.** With both arms
   patched, throughput reproduced at 80.6 / 78.3 tok/s — indistinguishable from the
   baseline-vs-patched runs (80.3) — while the acceptance still differed between the two identical
   arms. So the +37…46 % band is a property of the configuration, not of a lucky acceptance run.
2. **The acceptance itself is noisy in the patched configuration** (0.55–0.69 across five runs of the
   *same* configuration, versus 0.53–0.58 for the baseline across five). The baseline's tight band
   and the patched arm's wide band is the asymmetry the architect's mechanism ranking predicts:
   INT4 quantization of the draft head narrows/flattens the draft's logits, so near-ties flip, and one
   flipped draft token re-routes the whole continuation under the sampler's penalty state — which
   shows up as run-to-run variance rather than as a systematic shift. That is a **sampling-variance**
   explanation, not yet a correctness finding.

**What still separates "noisy but correct" from "nondeterministic kernel":** a seeded determinism
decomposition — greedy + fixed-nonce repeats with token-ID hashes (determinism), then seeds 1–5 with
two relaunches (variance split), then head-only vs MTP-only arms (localization). Until that runs,
the honest claim stays: *throughput +37…46 % reproduced; acceptance interpretation open; emitted
tokens remain target-verified by construction of speculative decoding.*

## 16. Greedy determinism decomposition — the pair is output-preserving

Run: champion harness in `DET=1` mode (greedy, `top_k=1`, fixed nonce prefix identical across arms,
three fixed prompts × two repeats per arm, `max_tokens=96`), baseline arm vs draft-pair arm. Evidence:
`results/2026/09/b70-improvement-probes-20260920/p4-champion-ab-p512-n2-…-20260921T122542Z/`.

| task | baseline sha256 (both repeats) | pair sha256 (both repeats) | verdict |
|---|---|---|---|
| numbers 1–40 | `3d28c8c35bd2beb9` | `3d28c8c35bd2beb9` | **identical** |
| twelve months | `8b0dcff966ecb7dd` | `8b0dcff966ecb7dd` | **identical** |
| alphabet | `71c480df93d6ae2f` | `71c480df93d6ae2f` | **identical** |

- **Within-arm determinism: OK in both arms** (byte-identical repeats on all three tasks).
- **Cross-arm identity: SAME on all three tasks** — quantizing the draft's LM head and MTP body to

  weight change should behave given that every emitted token is target-verified.

**Therefore the §14 "correctness-shaped signal" is resolved in the patch pair's favour**: the

change in what the model emits. Combined with §15 (throughput reproduced under a both-arms-patched
control), P4's headline claim now rests on: a robust +37…46 % throughput effect, an unchanged greedy
output, and an acceptance metric that simply should not be quoted as a fixed number for this
configuration.

**Remaining limit, stated so it is not over-claimed:** greedy equivalence is proven here. Under the
*recommended sampling* configuration the emitted distribution should be the target's by construction
of rejection sampling, but that is a property of the sampler rather than something this probe
measured locally; a distribution-level check (per-position logits or a large-sample agreement test)
is the honest way to close it. The claims-audit fix list (metric naming, patch-generation provenance,
energy/temp telemetry) is otherwise unaffected by this result.

## 17. Seeded sampled path — consistent, but the prompts were weak discriminators

Run: `DET=1 DET_SAMPLING=recommended DET_SEED=7` (temperature 0.7, top_p 0.8, top_k 20,
presence_penalty 1.5, fixed seed, three fixed prompts × two repeats per arm). Evidence:
`results/2026/09/b70-improvement-probes-20260920/p4-champion-ab-p512-n2-…-20260921T135800Z/`.

| task | baseline (both repeats) | pair (both repeats) | cross-arm |
|---|---|---|---|
| numbers 1–40 | `3d28c8c35bd2beb9` | `3d28c8c35bd2beb9` | **same** |
| twelve months | `8b0dcff966ecb7dd` | `8b0dcff966ecb7dd` | **same** |
| alphabet | `71c480df93d6ae2f` | `71c480df93d6ae2f` | **same** |

**Read it for what it is.** The seeded arms agree exactly — supportive evidence that the draft-side

**The test that would actually earn the claim** (recorded as the next step, not done): open-ended
prompts where sampling genuinely diverges, N ≥ 30 seeds per arm, and a comparison of the *emitted
distribution* (e.g. first-token choice frequencies and per-position agreement rate) rather than
per-prompt hashes. Only then may the phrase "distribution-preserving under recommended sampling"
appear in any claim, and even then it is a statement about this sampler configuration rather than a
proof.

## 19. Concurrency knee — a second, stackable lever (2.3–2.4× aggregate)

Run: the champion harness in `CONC=1` mode (one server, one config, 8 requests per level with B in
flight, greedy, ignore_eos, unique nonce per request, one discarded warmup), at C1 p512/g128.
Evidence: `…/p4-champion-ab-p512-n1-…-20260921T143215Z/` (baseline config) and `…T143819Z/`
(draft-pair config), `conc-B*.jsonl` in each.

| in-flight B | baseline config aggregate | patched config aggregate | patched per-request post-first |
|---:|---:|---:|---:|
| 1 | 48.45 tok/s | 61.86 tok/s | 72.36 |
| 2 | 69.73 (+44 %) | 85.40 (+38 %) | 64.97 |
| 4 | **115.70 (+139 %)** | **140.30 (+127 %)** | 48.54 |
| 8 | 119.82 (+147 %) | **149.79 (+142 %)** | 38.92 |

All 8 requests completed at every level with server-reported 128 output tokens each
(`token_counts_ok=True`), so nothing here is a truncated stream. Per-request latency degrades as
concurrency rises (TTFT grows from ~0.35 s to seconds at B≥4), which is the expected trade.

**Why this matters and what it is not.** The mechanism the architect predicted holds: in a fused
batch the weights are read once for all sequences, so per-sequence weight traffic falls roughly as
1/B and aggregate throughput rises steeply — measured **2.39×** by B=4 (baseline config) and **2.27×**
(patched). It also **stacks** with the draft-side INT4 lever: the patched config's B=1 (61.86) is
already above the baseline's (48.45) and its B=4 reaches **140.30 tok/s** against the baseline
config's 115.70 at the same level.

**Framing limits, stated up front:** these are *aggregate* rates over 8 concurrent requests, not
single-stream numbers, so they must never be compared to single-stream records — including this
route's own recorded 102.61 tok/s champion, which is a C1 single-stream cell. The correct claim shape
is: *on this route and cell, concurrency multiplies aggregate throughput ~2.3–2.4×, and the
draft-side INT4 lever stacks on top of it.* Per-request latency is the price and must travel with any
such number.
