## 0. Blocking discovery: the local BF16 source is a symlink stub farm

The task premise "BF16 source at `/mnt/<sata-disk>/Qwen3.8-27B-BF16/`" is FALSE
at tensor level: all 18 `model-000NN-of-00018.safetensors` entries are symlinks whose
targets (`qw38-bf16/` on the WD mount, `qw38-bf16-shards/` on T-FORCE) do not exist —
exactly as recorded in `docs/operations/storage-and-vram-safety.md` §9. The QUANT worklog
of 2026-09-24 verified only `config.json` (explicitly "no tensor reads"). A host-wide
search found no intact BF16 copy on any mount or HF cache (the hub cache entry is a 12 KB
refs-only stub; the NVMe staging copy named in the storage doc was already deleted).

Resolution (minimal, source-preserving, storage-budgeted): the single shard holding ALL of
layers 30+31 (`model-00009-of-00018.safetensors`, per the intact local index.json) was
fetched from the canonical public repo `Qwen/Qwen3.8-27B` (Apache-2.0) into an explicit new
staging path on the WD mount (76 GiB free; root fs at 99% was rejected):
`/mnt/<sata-disk>/tmp/qwen27-rotation-t1t2-20260925/`. sha256 verified identical to
the HF LFS oid: `af3c48cc37af44f3db6ae0579baf019180d48d9c527caa0a1f03ff85813a56d8`.
The local source dir was NOT touched (post-run integrity recheck below). The staging copy
is retained for tonight's session (re-runs / more layers without a re-download); deleting
it needs only that sentence, it is not a source artifact.

## 1. Method

- Blocks: layer 30 (`linear_attention` GDN) and layer 31 (`full_attention`), adjacent,
  mid-network. Forward = transformers 5.16.1 reference classes
  (`Qwen3_5DecoderLayer`/`GatedDeltaNet`/`Attention`/`MLP`/`TextRotaryEmbedding`), pure-torch
  fallbacks, BF16 module arithmetic, GDN recurrence in float32 per the reference code
  (matches `mamba_ssm_dtype: float32`). CPU only, 8 threads, d11-venv (torch 2.9.0+cpu).
- Rotation: `H_5120 = D (K_20 ⊗ S_256)/sqrt(5120)`; K_20 = Paley type-I over GF(19)
  (exact-orthogonality asserted; first construction attempt had a border bug, caught by the
  assert and fixed before any measurement); S_256 Sylvester; D Rademacher, seed 20260925.
  Residual-stream rotation only. RMSNorm gains pre-folded into readers (standard QuaRot
  step; Qwen3_5RMSNorm applies `(1+w)`), then readers `W@H`, writers `H^T W`, all
  re-rounded BF16 (deployable form). Internal spaces (GDN v/qk spaces, conv1d on QKV,
  RMSNormGated, q/k norms, RoPE, gates) left unrotated per the §4 foldability map.
  Worklog-map correction: the causal conv runs on QKV channels (with SiLU), NOT on a/b.
- Inputs: REAL activations — D11 final-layer (post-layer-63) residual states
  `prepared_d11_1500/hidden_states/hs_*.safetensors` ([seq,1,5120] F16 + token_ids),
  provenance = deployed GPTQ-INT4 champion + MTP (captured 2026-09-24 for D11). Cast to
  BF16. Eval: hs_1003 (350 pos), hs_1004 (471 pos). Calibration (T2): 12 sequences,
  5438 rows (amended pre-measurement from the originally declared 4 files = 1967 rows,
  which left the 5120-dim Hessian rank-deficient; manifest addendum, gates unchanged).
  The bounded-GPU capture exception was NOT needed.
- Quantizer (T2): verbatim port of the classic IST-DASLab GPTQ sym=True quantizer
  (zero-inclusive range, sym zero = 8.0, clamp(round(x/s)+z, 0, 15)) + FasterQuant loop
  (blocksize 128, percdamp 0.01, upper-triangular inverse-Hessian Cholesky, group 128,
  static column order) — matching the champion recipe contract (`qw38-quant/quantize.py`:
  bits=4, sym=True, group_size=128, desc_act=False; in_proj_a/b + conv1d excluded, exactly
  the champion's 400-qweight accounting: 48*6 + 16*7 = 400).
  Validated on real layer-30 weights with real activations: calibration-weighted
  reconstruction error GPTQ 0.0282/0.0272 vs RTN 0.1119/0.1166 (gate_proj/in_proj_qkv).
  Two defective drafts were caught in-run by per-tensor diagnostics and never produced
  recorded results (manifest addendum §9 records both).

## 2. Declared gates (manifest, BEFORE measurement)

- T1 (per block): min-position cosine >= 0.9999 AND max-position (max-abs delta / ref RMS)
  <= 5.0e-2. Arms: A original; B gain-fold-only (diagnostic); C deployable fold (primary).
- T2 (per block): top1(Q1) >= top1(Q0) - 0.005 AND meanKL(Q1) <= 1.1 x meanKL(Q0), where
  Q0 = unrotated GPTQ W4-G128, Q1 = rotated GPTQ W4-G128 (fold, quantize, run rotated,
  fp32 un-rotate for comparison). Q1bd (online block-diag 17x H_1024 before down_proj) and
  Bq (gain-fold-only quant) are secondary/diagnostic, no gate.

Reading: the declared 5e-2 max-abs tolerance sits BELOW the floor that ANY BF16
weight-rewrite (or even one extra state rounding) produces on this model's real
activations: the pure norm-gain fold — exact in exact arithmetic, no rotation at all —
already yields 0.17-0.23. The rotation adds nothing beyond that floor (S1 ~= C; C ~= B + S2
noise). Cosine equivalence holds at 0.99999+ per position on both blocks, including the
GDN block (hybrid-GDN rotation numerics are NOT catastrophically broken — that was the open
T1 question). Equivalence holds in the cosine sense and at ~1.2 % relative on the worst
outlier channel; it does NOT hold at the declared absolute 5e-2 line, for reasons that are
format-floor, not rotation-specific.

## 5. Limitations

- Inputs are REAL but distribution-shifted twice (champion-INT4 model, final-layer states
  fed to mid-network blocks). Same inputs feed every arm, so arm comparisons are internally
  valid; absolute realism of layer-30 inputs is not claimed.
- Two blocks out of 64; mid-network only; one Hadamard seed (QuaRot's random rotations can
  vary; SpinQuant's learned-vs-random axis untested); v-space rotation untested;
  17408-space smoothing only in the online-cost Q1bd arm (block-diagonal, no cross-block
  mixing — the declared fallback).
- top-1 "agreement" is a residual-channel argmax statistic (no LM head at block scope);
  KL is over softmaxed standardized hidden rows — both are declared proxies, NOT task
  quality (`logit_or_KL_parity_tested` < `task_quality_tested`).
- GPTQ calibration is 5438 real rows (12 sequences), not the champion's 128 wikitext texts;
  both arms share it, so the comparison is fair; the absolute error level may differ from a
  full conversion.
- No speed claim of any kind; T1/T2 say nothing about tok/s.

## 6. Implication for the W3 kernel-escalation decision (one paragraph)

Tonight's T1/T2 data do NOT justify opening a W3 (INT3 / new-kernel) program, and they DO
justify keeping the weight-only rotation branch alive as a W4-quality play. The W3 line's
standing blockers are unchanged and upstream of quality: the champion vLLM/XPU stack has no
INT3 loader, packing, or kernel (loader TYPE_MAP {4,8}, oneDNN `f16_int4`/`bf16_int4` with
no `num_bits`), and the step-byte bound for a 4->3 body is at most 1.215x — a new-kernel
program whose best case is ~20% byte savings on a stack already measured at 75-89% of its
byte floor. What T1/T2 add is the quality side: rotation is numerically well-behaved on
this hybrid-GDN architecture (cosine >= 0.99999; the only gate failure is a max-abs
tolerance set below the BF16 re-rounding floor that even a gain-fold-only refactor
breaches) and it buys a REAL, measurable quality margin at unchanged W4-G128 bytes
(KL 0.40-0.58x, top-1 +0.1-0.25 pts on both block types). That is exactly the parked P8
framing: quality/capacity at iso-bytes, no speed claim. Recommendation for tonight:
CLOSE the W3/INT3 kernel-escalation line on the existing loader/kernel/arithmetic gates
(nothing in T1/T2 moves them), and SPEC (do not yet build) the next rung of the W4
rotation branch: T3 whole-model fake-quant parity with the same H seed (seed 20260925)
against a re-derived BF16 source — noting the source itself must be re-fetched first
(§0), and that T3 requires ~55 GB of intact BF16, which the host currently lacks. If the
W4-quality margin survives T3, the payoff is headroom for a FUTURE more-aggressive
recipe (e.g. mixed G64/INT3-class bits within W4 kernels' reach, or better robustness at
the existing recipe), not a serving change today.
