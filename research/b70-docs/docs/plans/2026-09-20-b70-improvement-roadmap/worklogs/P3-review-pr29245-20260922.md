# P3 review — llama.cpp PR #29245, and the upstream stack state

**PROVISIONAL — NOT FOR PUBLIC HEADLINE.** Review performed read-only by the
Xe2 kernel engineer on 2026-09-22/23 against #29245 head
`ecce82ba1eb853fa4bce75f1b411452621932f21` and #29107 head
`acec95995f522adbd05a988c38315f0c5748a2d8` (both OPEN). No GPU work, no
compilation, no cherry-pick, no source edits, no upstream interaction.

## Verdict

**Extend #29245; do not build a competing grouped-GEMM implementation.** But its
current kernel does **not** satisfy the architect's no-split-K or zero-host-sync
requirements — those need an explicit ruling before we adopt it as-is (see
§Approval blockers).

## A. What #29245 actually implements

- **Formats: only IQ4_NL and IQ3_S. IQ3_XXS is absent** from reconstruction,
  traits, eligibility, and both launch switches
  (`ggml/src/ggml-sycl/fused-gemm.cpp:70–115`, `:335–345`, `:387–397`;
  `fused-gemm.hpp:11–29`). This is exactly our differentiator: the K216
  artifact is IQ3_XXS.
- **Geometry (axes transposed vs our spec):** 16 output features × 32 routed
  rows, K-stage 32; **four SIMD16 sub-groups, 64 work-items**. Each sub-group
  handles one contiguous quarter of K.
- **SLM: 12 KiB/WG** (4 KiB reconstructed weights + 8 KiB FP32 partial results).
  No activation tile, no RAW staging, no explicit SLM lookup tables
  (`fused-gemm.cpp:7–20, 275–283`) — materially leaner than our ~49 KiB plan
  because it keeps no activation tile resident.
- **Reconstruction is genuinely tile-local.** IQ3_S fields are read directly from
  global blocks and reconstructed into sub-group-private SLM regions;
  whole-expert FP16 weights are **not** materialized. This is the mechanism we
  want, already working for two formats.
- Activations are separately gathered, rounded F32→F16 and globally VNNI-packed,
  including padded rows (`:287–309`). That residual traffic is not whole-expert
  weight expansion.
- **Scheduling:** host-built expert-major tile descriptors uploaded once, then a
  conventional grouped launch — **not** 32 persistent work-groups (`:350–400`).
- **Host synchronization remains:** `ggml-sycl.cpp:5145–5152` still copies IDs
  D2H and `stream->wait()`s; the grouped call happens after, at `:5242–5249`.
- **MMQ remains disabled:** `ggml_sycl_supports_mmq()` still returns false
  (`:4004–4007`). The PR bypasses whole-weight conversion through a separate
  path rather than repairing the dormant MMQ route.

## Correctness and implementation risks

1. IQ4_NL nibble placement and nonlinear table scaling match the reference;
   IQ3_S preserves nine-bit grid indices, explicit signs and
   `d*(1+2*scale_nibble)` before FP16 conversion (`fused-gemm.cpp:70–110`).
   **This is static agreement from reading, not measured bit parity.**
2. **IQ3_XXS `d*(0.5f+s)*0.5f` semantics are not implemented** — there is no
   existing XXS reconstruction to certify. Our extension must supply it
   (spec §5 is the source of truth for those semantics).
3. **Deterministic split-K:** `:156–157` partitions K; `:204–217` sums four
   partial results in fixed sub-group order. No numeric atomics and no cross-WG
   reduction — so it *is* deterministic — but it violates the explicit
   **no split-K** rule of spec §7 and changes accumulation rounding relative to
   a single-pass reduction. Needs a ruling (below).
4. FP16 operands + FP32 accumulation/output match the corrected dtype contract
   (spec [C3]) — but they do **not** guarantee bit-identical oneMKL outputs,
   because reduction order differs. Parity gate 3 (rel. squared-L2 ≤ 1e-5) is
   therefore the binding tolerance, not bit identity of outputs.
5. Weight SLM has 64-byte row strides; banking deserves profiling. Grid lookups
   are not staged in SLM, so the spec's grid-table bank-conflict diagnosis does
   not transfer directly.
6. Direct byte/half-field access avoids assuming 32-bit alignment of whole IQ
   blocks, but there is **no RAW staging**. For our 98-byte IQ3_XXS blocks,
   avoid unaligned `uint32_t*` loads of the scale/sign words — that is a real
   fault risk the spec's RAW pass exists to prevent (§10 F5).
7. Four 8×16 FP32 accumulators = **2 KiB/sub-group** plus live operand fragments
   and decode temporaries. **No compiler spill evidence accompanies the diff** —
   the zero-spill compile gate (spec §9 gate 5) is still unverified for this PR.
8. **Integration hazard (concrete):** stacking #29107 on #29245 can leave dense
   IQ3_S weights reordered while #29245's dense fused entry interprets them as
   ordinary block structs without checking the reorder flag. **Add a rejection
   guard before combining these paths.**
9. The device-capability cache is one function-static bool (`:311–314`), not
   per-device — wrong on heterogeneous multi-device hosts.
10. The PR adds **no regression tests**.

## Performance claim vs our arithmetic

- The author reports **274.101 → 368.298 prompt tok/s (+34.37 %)** for a Qwen
  IQ4_XS artifact — **not** K216 IQ3_XXS — and the workload/cap/repetition
  coordinates are missing, so it is not a matched comparison against our cells.
  The mechanism (fewer launches + tile-local reconstruction) makes the direction
  plausible, but it does not establish our ≥2× operator gate and does not predict
  K216's gain.
- Our all-expert arithmetic (exact): **693,633,024 IQ3 bytes;
  3,623,878,656 FP16 bytes written; 7,247,757,312 bytes written+read per op.**
  At the assumed 608 GB/s that round trip alone is **11.92 ms/op**, before IQ3
  reads and compute — i.e. the waste we are removing is real and large.
- The 1.141 ms bandwidth and 0.281 ms XMX component bounds are **optimistic and
  not additive** (execution may overlap); repeated token tiles may reread weights.

## B. Recommended minimal contribution (Sergio's rule: minimal PR)

**Sequence:** (1) the operator coordinates with `cwriter`; (2) we prepare a small
**IQ3_XXS extension stacked on #29245**, with tests; (3) device-side scheduling
and architecture retuning stay separate (never in the same PR).

Delta list for the extension:

- add `fg_stage_a(const block_iq3_xxs *, …)`;
- add `fg_block_traits<block_iq3_xxs>`;
- add XXS type eligibility and XXS cases in **both** fused and grouped launch
  switches;
- reuse the existing `iq3xxs_grid` and `ksigns_iq2xs` tables verbatim (spec §10
  F8: never regenerate);
- for stage `kb`: block `kb/8`, sub-group `kb%8`; preserve the 64-byte grid-index
  region, the eight scale/sign words, the four 7-bit sign indices, the **ordered
  FP32 scale multiplies** (`db = d*(0.5f+s)*0.5f`), and the final FP16 rounding;
- **no 216-expert specialization needed** — the existing scheduling is
  parametric, and 3072 routed rows / 216 active experts passes its ≤64
  average-row gate.

Tests the extension must add: reconstruction bit tests; both K216 shapes
(gate/up `m=2048,n=512,k=4096` and down `m=4096,n=512,k=2048`); broadcast and
per-slot activations; empty and skewed experts; tail rows; decode→prefill layout
transition tests. Retain the full gate ladder: finite outputs, rel. squared-L2
≤ 1e-5, NMSE ≤ 5e-4, zero-spill compile gate, **isolated op ≤ 14.4 ms** (≥2× vs
the 28.87 ms recapture), then **≥15 % matched end-to-end prefill**.

## Approval blockers (need a ruling before adoption)

1. **Deterministic intra-WG split-K** in #29245 contradicts spec §7's no-split-K
   rule. It is deterministic (fixed sub-group order, no atomics) but changes
   rounding. **Needs an explicit architect ruling or a separate non-split kernel
   variant.**
2. **Host scheduling is a policy exception, not "sync eliminated."** The D2H ID
   copy + `stream->wait()` survives at `ggml-sycl.cpp:5145–5152`. AGENTS §17 rule
   5 (on-device router-to-GEMV dispatch) is not satisfied by this PR.
3. The message to `cwriter` **must be written by the operator personally**:
   `llama.cpp/AGENTS.md:88–98` forbids AI-written upstream comments, including
   drafting them on the user's behalf. What it should cover, in the operator's
   own words: coordination on XXS support, the exact K216 shapes, reconstruction
   tests, and the split-K/layout concerns. Explicit AI disclosure, a reproducible
   issue, and `llama-perplexity`/`llama-bench` non-regression evidence are all
   required by that project's contribution policy.

  IQ3_XXS/IQ3_S device-ID dispatch. On rebase, **drop only our redundant local IQ3

  4797–4802` and `mmvq.cpp:3140–3157` still restrict MoE reorder to
  Q4_K/Q5_K/Q6_K. Its plain IQ3 dot-product rewrite **does** reach fused routed
  decode through #28476's adapters; dense IQ3 reorder sits beside that. The
  reported **+75.5 % is therefore NOT a demonstrated K216 routed-reorder gain** —
  treat it as a decode-dot-product lever only.
- CPU arithmetic check of #29107's new sign transformation passed all **128
  encoded signs and 4096 XXS packed-grid/sign combinations**. That is a static
  arithmetic check, not floating-point or kernel parity.
- **Minimal decode experiment (later GPU window):** transplant only the IQ3
  sign/dot changes and the corresponding adapter/caller signatures onto the
  upstream-dispatch baseline; avoid the full `acec959…` commit's unrelated
  normalization, fusion and CMake changes. Cherry-pick applicability is still
  untested. **Kill probe:** matched K216 n=1 gate/up and down operator
  parity/timing, then matched L5 end-to-end decode; stop on parity failure or
  absent operator improvement. True routed reorder additionally needs per-expert
  repacking, ID eligibility/dispatch, reorder-aware prefill, and transition tests.

## What this changes about the roadmap

- P-3's execution shape is now **"IQ3_XXS extension on #29245"**, 2–5 days, with
  the extension delta above — not a from-scratch kernel. The physics and the gate
  ladder are unchanged.
- The decode lever that looked like a +75 % gift (#29107) is **narrower than the
  headline**: it is a dot-product rewrite that reaches routed decode, not a
  routed reorder. Re-measure before quoting anything.
- Our uncommitted device-ID cases are confirmed **redundant as of #28476** and
  should be dropped on rebase (OUTCOMES L7's wording correction now also needs
  "and since merged upstream as `304665fe7`").
