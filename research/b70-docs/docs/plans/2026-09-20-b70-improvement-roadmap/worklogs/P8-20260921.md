# P8 worklog — AWQ branch, 2026-09-21

Phase: P8 (bounded quant screen), AWQ branch. Status entering: `RESEARCH` (entry gate passed:
the AWQ loader resolves to an existing XPU op). This run is the "narrow artifact probe" the phase
asks for before any conversion work.

Artifact tested: `cyankiwi/Qwen3.8-27B-AWQ-INT4` (downloaded, 21.0 GB) on the local
vLLM XPU image, GPU 1, 230 W. Harness: `scripts/tmp/p8-awq-screen-20260921.sh` + `p8-awq-suite.py`.
Evidence: `results/2026/09/b70-improvement-probes-20260920/p8-awq-20260921T115440Z/`.

## What the probe found

1. **It loads and serves cleanly** — `load_ok=1`, 5,075 MiB free after load, all suite requests 200.
2. **It does NOT exercise the AWQ loader path.** The engine's own config line reports
   `quantization=compressed-tensors` for this checkpoint, i.e. the artifact declares
   compressed-tensors and vLLM loads it that way. So the AWQ-specific route
   (`auto_awq.py:304` → `AutoAWQMarlinLinearMethod` → `int4_gemm_w4a16`) remains **source-verified and
   falsification-tested but not end-to-end exercised by this artifact**. That is a correction to what
   the download was expected to test.
3. **It is not an iso-byte artifact**, which is the one property P8's AWQ branch actually needs:
   language-only tensor bytes **20.10 GB vs the champion's 18.63 GB = 1.079×** (+1.47 GB). (Both
   artifacts carry the same 0.92 GB of non-language tensors; the comparison above excludes them and
   the raw-shard ratio is 1.075 — either way, ~8 % larger.) So this artifact cannot answer
   "quality at iso-bytes" against the GPTQ champion.
4. **Bounded correctness signal**: 5 of 6 tasks correct (arithmetic chain, letter ordering, token
   counting, an errno constant, a C `sizeof`, a date computation). **One of the six is ill-posed by
   my own construction** — `((17*23)+19-5)/11 = 36.8` is not an integer, yet the prompt demanded a
   number only, so the "expected 36" check is wrong and that item must not be read as a model
   failure. The suite needs one arithmetic item with an exact integer answer before its pass rate
   means anything.

## Consequence for P8

- The **AWQ loader/kernel conclusion stands** (it was established from source + the wheel's op
  listing, and confirmed present in the deployed wheel), but the end-to-end AWQ dispatch claim is
  **not** established by this run.
- The AWQ branch's next step is unchanged in kind but now precisely specified: obtain or build an
  AWQ-declared, **iso-byte** W4A16 artifact (same 18.63 GB language-only weight budget), then run
  the quality screen against it. A conversion from the local BF16 source with a declared AWQ group
  size is the honest way to get iso-bytes; downloading another community artifact risks the same
  mismatch.
- Until then P8's answer to "quality-per-byte for AWQ" is **open**, and nothing here supports a
  speed claim (AWQ shares the W4A16 arithmetic, as the phase already states).

## Addendum — the AWQ format question is closed by ecosystem evidence

Five community artifacts advertised as AWQ for this model were checked at their `config.json`
(cheap reads, no downloads): `cyankiwi/Qwen3.8-27B-AWQ-INT4` and `…-AWQ-BF16-INT4`,
`philbert440/…-W4A16-AWQ`, `TheUnderscore/Swift-…-W4A16-AWQ`, `ulkaa/…-AWQ-INT4`,
`abihsoro/…-AWQ-INT4`. **All five declare `quant_method=compressed-tensors`; none declares `awq`.**

That closes the AWQ-format half of this branch: the checkpoint format the phase wanted to screen is
not what the ecosystem produces for this model, and the class that *is* produced —
compressed-tensors W4A16 — was served successfully by the screen above. What remains for P8 is the
iso-byte quality comparison on that class, for which an artifact ~8 % larger than the champion does
not qualify. Nothing here is a speed finding; both paths share the W4A16 arithmetic.
