## 2. Per-point findings

### Point 1 — vLLM XPU / Intel-extension: graphs, compile, spec-decode, INT4, FP8 KV

**XPU graph capture status.** PyTorch 2.9 introduced a "Graph API [that] unifies graph capture and replay across CUDA, XPU, and out-of-tree backends" (https://github.com/pytorch/pytorch/releases; blog: https://pytorch.org/blog/pytorch-2-9/). `torch.xpu.graph` / XPUGraph exists in current docs (https://docs.pytorch.org), tracked by RFC https://github.com/pytorch/pytorch/issues/162143. Intel discontinued IPEX feature development after 2.8, moving XPU features into core PyTorch (https://github.com/intel/intel-extension-for-pytorch — "[IMPORTANT] The future of Intel® Extension for PyTorch", Oct 2025); Intel's dev-discuss roadmap lists "Advance XPUGraph integration in PyTorch" (https://dev-discuss.pytorch.org/t/intel-gpu-cpu-enabling-status-and-feature-plan/21868).

**The concrete B70 + MTP + graph-capture bug cluster** (vLLM #56917, open, labeled intel-gpu + speculative-decoding, https://github.com/vllm-project/vllm/issues/56917) reports on 2x B70 with TP=2, Qwen3.8-27B INT4 + MTP:
1. "Graph capture doesn't engage under TP=2 by default … forces eager execution for every kernel of a 60-layer model."
2. MTP speculator capture crashes "in `speculator.py` → `cudagraph_utils.py` → `torch/xpu/graphs.py:192`, because `torch.xpu.synchronize()` [is] called while a queue is still recording into a command graph."
3. "No available shared memory broadcast block found in 60 seconds" hang at concurrency 3–5 (suspected engine reset stalling a collective).

These TP2 reports are distinct from the single-card fused QK dispatch screen. Upstream archaeology found the equivalent #53989 dispatch merged as vLLM **#56096** (https://github.com/vllm-project/vllm/pull/56096); our older-image local screen is recorded as RL-054 and did not promote (overlapping ranges, acceptance guard exceeded, thermal protocol invalid; dispatch not traced). **Do not file duplicate #53989 work.** PR #53997 (keep grammar-bitmask copies on the current stream under XPU graphs) remains a separate untested graph-safety candidate; #53990/#53996 and issues #53992/#53993 remain separate items. The fork reports "within 1-5% of bare metal" and 57/203 tok/s; those external figures are not local B70 evidence. A related closed bug: #53993 "[Bug]: [XPU] V2 model runner fails under XPU graphs: grammar-bitmask copy_stream wait_stream inside SYCL graph recording" (closed Aug 27, 2026, https://github.com/vllm-project/vllm/issues/53993). Watch PR #58082 "[Refactor][Core] Use torch's device-agnostic streams and events in the V2 model runner" (open, Sep 22, 2026, mrv2 + speculative-decoding labels, https://github.com/vllm-project/vllm/pull/58082).

**Kernel-library migration (IPEX → vllm-xpu-kernels).** RFC #33214 (https://github.com/vllm-project/vllm/issues/33214): INT4 `compressed_tensor_w4a16` merged (PR #33973); FP8 w8a16/w8a8 `scaled_mm` merged (PR #34117); FP8 MoE (#34202), MXFP4 MoE (#33679), unquantized MoE (#33659) merged; **INT4 GEMM for AWQ/GPTQ still WIP (PR #33662)**; INT4 MoE listed without status. Scope note: "we only touch kernel part, other feature like torch.compile should not be affcted."

**Release notes with cherry-pickable items** (https://github.com/vllm-project/vllm-xpu-kernels/releases):
- v0.1.15 (Sep 22, 2026): "Improved top-k/top-p sampling and added per-row RNG state support and a compact sampling-mask op"; "Added fused XPU LayerNorm kernels for the eager path"; "Improved Xe2 BlockFP8 grouped-GEMM performance by applying scaling in the accumulator"; Xe3P chunk-prefill/paged-decode attention; `VLLM_XPU_ENABLE_ONEDNN` build toggle.
- v0.1.14 (Aug 31): "Added a SYCL implementation of fused_kv_compress_norm_rope_insert_sparse_attn for DeepSeek-V4"; "fp8_gemm_out variant that writes directly into caller-provided buffers"; "Fixed mixed speculative and non-speculative GDN workloads."
- v0.1.13 (Aug 13): oneDNN v3.13; "fused-MoE capability updates, including TopK-16 support and SITU activation support"; "new SYCL reorder_mxfp_scales kernel"; "Enabled native Xe2 grouped-GEMM paths for MXFP8 and block-FP8 MoE execution."

**FP8 KV + INT4 weight GEMM fusion.** No XPU implementation found. Nearest design: FireQ (INT4 weights + FP8 scales W4A8, RoPE-aware KV quant, Hopper-only, ~1.68x) https://arxiv.org/abs/2505.20839. vLLM's own FP8-KV state-of-the-art writeup: https://vllm-project.github.io (2026). Nothing XPU-specific about "CUDAGraph aliasing" surfaced; the open XPU-graph bugs are the stream/event ones above.

### Point 2 — Level Zero / SYCL graph capture for MUL_MAT_ID-style ops

**llama.cpp PR #28725 "Add SYCL graph record and replay"** (open, Sep 10, 2026, Intel author malsbat; https://github.com/ggml-org/llama.cpp/pull/28725). Direct quotes from the PR:
- Feature gated by `GGML_SYCL_ENABLE_GRAPH=1`; recorded graphs cached and replayed ("record, play, play…"); stale-graph eviction via `GGML_SYCL_GRAPH_EVICTION_TIMEOUT`.
- SYCL async memory allocation "leads to a hang during graph recording" — fixed in intel/llvm PR #21170, workaround gated on oneAPI version (removable past 2025.3.3).
- Library GEMM calls fail with "Graph nodes cannot depend on events from outside the graph" — but "the author later found this restriction unneeded with oneAPI 2026"; however "shape-dependent `wait()` calls remain a problem (ubatch 1024 hits a stream wait; 512 doesn't)."
- **"`MUL_MAT_ID` is excluded due to a memcpy+wait, which makes the PR ineffective for MoE models."** — This is precisely the host-sync our device-ID repair removes; our local patch is the enabling prerequisite for capturing the MoE path.
- Numbers: A770 i915 tg128 29.12 → 44.28 t/s; **B70: "negligible change (±1%, within noise)"** on a dense model; mndodd (separate): Qwen 35B-A3B **+19.8% decode with `SYCL_GRAPH_FORCE_NATIVE_RECORDING=1` plus Level Zero patches** — i.e. the MoE exclusion can be bypassed via native recording + L0 work.
- Files touched: `ggml/src/ggml-sycl/common.hpp`, `ggml/src/ggml-sycl/ggml-sycl.cpp`.

**SYCL graph extension semantics** (https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_graph.asciidoc):
- Record & replay: `graph.begin_recording(queue)`; events from outside the recording scope throw "a synchronous error … with error code invalid" (matches the PR's GEMM failure).
- Native backend recording: `property::graph::enable_native_recording`, and "DPC++ also honors `SYCL_GRAPH_FORCE_NATIVE_RECORDING=1`" — the exact env used in the +19.8% MoE report.
- Host tasks "may prevent the SYCL runtime from submitting the entire executable command_graph to the device at once"; under native recording `handler::host_task` is unsupported.
- `dynamic_parameter` node-argument updates allow replay with new scalars/pointers without re-recording (useful for batch-size-variable decode); graph update requires `property::graph::updatable` and topological identity.
- "CGF code is captured once" — any host-side branching inside the capture lambda is frozen at record time.

**Level Zero layer.** The SYCL graph lowers to the backend's native graph capture; the experimental command-graph APIs live in the level-zero headers (https://github.com/oneapi-src/level-zero; spec: https://oneapi-spec.uxlfoundation.org). No stable public `zeCommandGraph*` documentation surfaced beyond the extension headers — implementation work should go through SYCL native recording first and drop to L0 only if needed.

**Implication for K216:** the "SYCL graph-capture prerequisite" verdict from p1-k216-e2e-ab is consistent with upstream: the memcpy+wait in `MUL_MAT_ID` is exactly why upstream excludes MoE. Our device-ID patch removes the wait; PR #28725 + native recording is the remaining scaffolding. Expected payoff on this host is bounded by the fact that the routed op runs 5.52x above its weight-read floor (kernel efficiency, not launch), so the gate stays ≥10% matched E2E.

### Point 3 — Grouped GEMM / MoE prefill kernels; no whole-expert FP16 materialization; XMX sub-byte

- **"Scaling in the accumulator"** (vllm-xpu-kernels v0.1.15, BlockFP8 grouped-GEMM): fold the per-block scale into the DPAS accumulator instead of materializing dequantized operands — the exact "no whole-expert FP16 materialization" pattern, already shipping on Xe2 for FP8. An IQ3 analog needs a block-dequant-to-FP16-tile fused GEMM (dequant-in-register), or an INT4 pre-shuffled layout.
- **Machete** (Neural Magic/Red Hat, https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel-optimized-nvidia-hopper-gpus): mixed-input (W4A16) GEMM design built on **weight pre-shuffling** — reorder the sub-byte weights at load time so the compute loop reads contiguous native-width operands. This is the design ancestor of llama.cpp PR #29107's "persistent reordered layouts for IQ3_S and IQ3_XXS MMVQ" (which won +75–95% tg on B70/B60; https://github.com/ggml-org/llama.cpp/pull/29107). The same reorder idea applied to the prefill MMQ path (not just MMVQ) is our best concrete kernel proposal for the 28.87 ms/op routed projection.
- **Tile sizes:** CUTLASS added "128x32xK and 128x64xK tile sizes for SM120 blockscaled MMA collective builders, yielding up to 30% performance improvement" (https://github.com/NVIDIA/cutlass/blob/main/CHANGELOG.md) — narrow-N tiles are the current best practice for grouped/quantized GEMM; a good starting nd_range for an ESIMD prototype on XMX.
- **Triton on XPU is not ready for our MoE prefill**: intel/intel-xpu-backend-for-triton epic #6389 "[VLLM] Grouped GEMM Performance and Tuning" (Mar 17, 2026) states "The Triton XPU doesn't support to prefetch the column major B matrix of regular pointer. The token is not loaded by block IO" (https://github.com/intel/intel-xpu-backend-for-triton/issues/6389, sub-issues #6553/#6704, milestone 26). Intel's Triton merge SLA into upstream is 2–5 business days with the PyTorch 2.15 pin branch-cut ~mid-late Oct 2026 (https://github.com/intel/intel-xpu-backend-for-triton/issues/7757). Intel's "XPU Kernel Skill / Xe-Forge" LLM-driven Triton-kernel generator for Xe2 exists (https://huggingface.co/spaces, Jun 2026) — usable for pointwise/fused-epilogue experiments, not the grouped GEMM core.
- **XMX formats on Xe2:** XMX supports INT2/INT4/INT8/FP16/BF16/TF32 (https://www.techpowerup.com/review/intel-arc-b580/, https://chipsandcheese.com/p/intels-battlemage-architecture) — external confirmation of native INT4 DPAS; consistent with our rate-class law (INT4 is a bandwidth/capacity lever, never a compute multiplier over INT8; Battlemage has no FP8 DPAS).

### Point 4 — Draft-side quantization (asymmetric speculation)

- **Correctness anchor:** Leviathan et al., "Fast Inference from Transformers via Speculative Decoding": "Speculative sampling, and therefore speculative decoding, guarantee an identical output distribution for any choice of approximation model Mq" (https://openreview.net/forum?id=1fZ0tGfsqb; retrospective https://research.google/blog/looking-back-at-speculative-decoding/). Quantizing the draft changes only acceptance rate, never the output distribution — the theoretical basis for our draft-side INT4 win and for any further draft compression.
- **QSpec** (https://arxiv.org/abs/2410.11305): "decouples efficiency from quality by integrating two complementary quantization schemes via speculative decoding" — draft **W4A4**, target **W4A16**; published precedent for aggressive draft-side precision cuts with an intact target. Our measured W4A16-g128 draft result sits at the conservative end; a W4A8/W4A4 draft is a follow-on screen if acceptance stays within protocol bounds.
- **QuantSpec** (https://arxiv.org/abs/2502.10424, https://github.com/SqueezeAILab/QuantSpec): draft = same architecture with a "hierarchical 4-bit quantized KV cache" (KVQuant-style); target verifies. Shows the draft KV/MLP state (not just weights) is also a valid quantization axis for MTP-style drafters.
- **Pitfalls (measured in literature):** SpecMQuant (https://arxiv.org/abs/2505.22179, https://github.com/AI9Stars/SpecMQuant): "verifying a tree-style draft incurs significantly more time overhead than a single-token forward pass on 4-bit weight quantized models" — tree verification compute on an INT4 **target** can eat the memory-bandwidth win (they route around it with a small intermediate model converting tree→sequence drafts; 2.78x on Llama-3-70B A100, 1.31x over EAGLE-2). Our MTP4 tree verify is fused under XPU graph capture, which is why we still measured +37–46% — but verify-batch time must be watched, not just acceptance. EAGLE-3 acceptance also drops at concurrency (draft head acceptance falls as B grows; https://spheron.network/blog/eagle-3-speculative-decoding/). Known pitfalls summary: acceptance-rate collapse (worse than no draft), draft/target tokenizer or KV-layout mismatch, and greedy-vs-sampled labeling per protocol.

### Point 5 — vLLM V1 host-side hotspots at C1

- V1 architecture: "a simpler scheduler, near-zero-overhead prefix caching" (https://blog.vllm.ai/2025/01/27/v1-alpha-release.html); "async single-step scheduling" schedules step n+1 while the worker executes step n (https://github.com/vllm-project/vllm/issues/8779); API-server↔engine-core process communication is ZeroMQ (https://developers.redhat.com/articles/2025/01/28/vllm-v1-alpha-major-upgrade-vllms-core-architecture). Async scheduling is V1-only with caveats (https://docs.vllm.ai/en/latest/configuration/scheduler.html).
- Once XPU graphs remove device launch cost, the visible C1 remainder is exactly what the 2026 XPU work targets: **sampler** (v0.1.15 "improved top-k/top-p sampling … compact sampling-mask op"), **grammar bitmask copies inside graph recording** (#53993/#53997), **eager-path norm/act fusion** (v0.1.15 fused LayerNorm), and per-step host syncs (PR #58082 device-agnostic streams/events).
- The #56917 fork reaching "within 1-5% of bare metal" is the strongest external evidence that when graphs + spec decode work cleanly on B70, host-side overhead is nearly eliminated — i.e. after cherry-picks, further C1 CPU tuning has little left.
- Field reports (https://sergiiob.dev): "Graphs plus a BF16 DFlash draft. Native MTP still accepts 0%" and "MTP4 full graph capture deadlock" titles confirm the MTP+graph interaction is the fragile spot on B70 vLLM; our stack already runs the working side of this (graphs on, MTP4 champion).

## 4. Do not attempt (promising-looking, but sources show it won't work on Xe2/XPU today)

1. **Triton grouped GEMM for MoE prefill on XPU.** intel-xpu-backend-for-triton #6389: no column-major B prefetch, no block-IO token loading; epic still in "performance tuning" state (https://github.com/intel/intel-xpu-backend-for-triton/issues/6389). Write it in SYCL/ESIMD instead.
2. **FP8-KV + INT4-weight fused GEMM on XPU.** No implementation exists on XPU (vllm-xpu-kernels ships only separate FP8-KV fixes); the reference design (FireQ, https://arxiv.org/abs/2505.20839) is Hopper-specific (TMA/wgmma). High port cost, unproven benefit here.
3. **sglang-xpu on B70 now.** `intel_xpu` attention backend "produces garbage/incoherent output … from the very first request" (Jun 2026, https://github.com/sgl-project/sglang/issues?q=intel_xpu+B70). Re-check after the fix lands.
4. **Stock TP=2 on dual B70.** `intel/vllm:0.17.0-xpu` reproduces "a `VLLM::Worker` general protection fault followed by `xe` BCS engine resets" on dual B70 (May 2026 issue via https://github.com/vllm-project/vllm/issues/56917 and related reports); even the patched fork needs three fixes and still hangs at concurrency 3–5. Reinforces ADR-0008 independent-stack default.
5. **llama.cpp SYCL graphs on dense models as a B70 speed lever.** PR #28725 B70 result: "negligible change (±1%, within noise)"; gains are i915/A770/driver-specific and "highly model-specific" (https://github.com/ggml-org/llama.cpp/pull/28725). Only the MoE path via MUL_MAT_ID enablement + native recording is worth a gated attempt here.
6. **MTP / DFlash on llama.cpp SYCL.** "The kernel launch overhead (100-500µs vs ~5µs CUDA) dominates. 100% draft acceptance confirms this is dispatch overhead, not compute" (https://github.com/ggml-org/llama.cpp — SYCL MTP issue, May 2026, referenced from PR #28725 context); community: "Qwen 3.6 27b has some decent speed up when using MTP but slows down" in other configs (https://github.com — B70 SYCL MTP/DFlash issue, Jul 27, 2026); sergiiob.dev: "Native MTP still accepts 0%" on vLLM without the BF16-draft path. Matches our DFlash/DSpark no-go.
7. **Enabling MTP + XPU graphs on vLLM without the stream fixes.** Deterministic crash: `torch.xpu.synchronize()` while a queue is recording into a command graph (`torch/xpu/graphs.py:192`, #56917/#53993). Apply #53997/#58082 first or use `--enforce-eager` (which forfeits the 1.68x graph win).
8. **IQ3 reorder as a prefill lever.** PR #29107: "Prefill remained effectively unchanged" — decode-only. The K216 prefill budget remains the grouped-IQ3 kernel, not this PR.
9. **Expecting Xe3P hardware or new-driver features to help this host soon.** Crescent Island sampling H2 2026, launch possibly 2027 (https://www.techpowerup.com/news/?id=55285); nothing here changes Xe2 tuning now.
10. **Trusting Vulkan-backend XMX claims as a llama.cpp path.** "Swings by a factor of three between driver releases" (#27593); not reproducible-platform material under our protocol.
11. **Chasing >8-bit-equivalent compute from INT4 DPAS.** External XMX docs confirm INT4 support (TechPowerUp/Chips&Cheese) but our rate-class law stands: sub-8-bit operands do not add TOPS on Xe2; INT4 stays a bandwidth/capacity lever (https://chipsandcheese.com/p/intels-battlemage-architecture).
