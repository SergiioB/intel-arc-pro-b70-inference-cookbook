# registry/

Run `python3 tools/research.py next` for a compact view of the current decision.
The JSON files below remain the only state authorities; generated Markdown is for reading.

| File | Role |
|---|---|
| `research-program.json` | Three-focus portfolio, explicit holds, passed/rejected dependency resolution, ranked questions and deciding gates (`research/PROGRAM.md`) |
| `research-ledger.json` | Outcome record for work that ran — blocked/validated/failed/provisional with evidence (Markdown view: `research/LEDGER.md`) |
| `model-status.json` | Current route per model, open gates, dated external cross-checks (Markdown view: `models/STATUS.md`) |
| `campaigns.yaml` | Registered campaigns: ids, evidence roots under `results/`, narrative paths, evidence tier, publication state |
| `index.json` | GENERATED catalog of every document (front-matter scan; `tools/build-indexes.py`) |

Rules:

- JSON/YAML here is the authority; the Markdown views are generated by
  `python3 tools/research.py render` and checked by `... check`.
- Keep the three registries distinct: program = what is worth asking next,
  ledger = what happened, model-status = what serves now. Do not merge them.
- The 2026-08-30 YAML registry system (documents/legacy-results/artifacts/
  decisions/models/supersessions + migration schemas) is frozen at
  `archive/registry-system-20260830/` (generator tool recoverable at git
  `09356e50:tools/research_registry.py`).
- Editing registries: append-only for ledger rows; keep the three registries distinct (program / ledger / model-status); regenerate views with `python3 tools/research.py render`; run `python3 tools/research.py check` and `python3 tools/situation.py compile` after edits.

`research.py record` appends sealed experiment outcomes to the existing ledger
and campaign registry. It never promotes a serving route. Eligible screens are
`validated_screen`; confirmation candidates remain `provisional` until reviewed.
Keep one registry writer across Syncthing peers; local locks are not distributed.
