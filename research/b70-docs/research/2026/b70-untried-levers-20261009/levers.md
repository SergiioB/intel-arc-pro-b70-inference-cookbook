# Decode & Prefill Throughput Levers for Dual Intel Arc Pro B70 — Primary-Source Survey

Compiled 2026-10-09 for B70-DOCS. Scope: levers from 2023–2026 papers/GitHub that raise decode or prefill throughput and could plausibly apply to two Arc Pro B70s (Xe2/BMG-G31, 32 Xe2 cores, 256 XMX, 32 GB, 608 GB/s pin BW, 367 dense INT8 TOPS — Intel B70 datasheet: https://www.intel.com/content/dam/www/central-libraries/us/en/documents/2026-03/datasheet-b70-gpu.pdf, product page: https://www.intel.com/content/www/us/en/products/sku/245797/intel-arc-pro-b70-graphics/specifications.html). Repo-internal baselines are marked **(repo)**; first-principles math is marked **[INFERENCE]**; anything not confirmed from a primary source is marked **[UNVERIFIED]**.

## 0. Resource model every lever is judged against

- **Decode is bandwidth-bound**: tok/s = yield × achievable_BW / bytes_per_token. Measured **(repo)**: EXL3 M=4 verify pass sustains **381 GB/s** (63% of 608 GB/s pin); the residual 37–43% is lost *inside* kernels — trellis decode is instruction-issue-bound. So decode levers move one of: **bytes/token** (weight+KV format), **yield** (kernel efficiency / instruction count), or **tokens per bandwidth dollar** (speculative acceptance).
- **Prefill is compute-bound**: INT8 DPAS peak 367 TOPS (datasheet above); FP16 XMX ≈ half of INT8 (Xe2 XMX type scaling — INT8/FP16/BF16/TF32 supported, no FP8 in Xe2 XMX per Intel oneAPI GPU guide https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/xmx.html and third-party Xe2 analysis https://www.hwcooling.net/en/batttlemage-details-of-intel-xe2-gpu-architecture-analysis; repo's FP8 block route at 48 tok/s vs EXL3 4bpw 63.25 tok/s is consistent with no FP8 DPAS fast path **(repo)**). Prefill levers move **FLOPs/token** (attention sparsity, prompt length, dtype) or **TOPS utilization** (DPAS-friendly GEMMs, chunking).
- **Two cards are two islands**: copy-only P2P 11–12 GB/s, no peer atomics **(repo)**. Anything needing per-layer all-reduce (stock TP2) is blocked — exl3xpu plugin guard + xccl-only transport **(repo, registry)**. Cross-card levers must be **one-shot or overlappable copies**, not collectives with atomics.

## 1. Speculative decoding (moves: accepted tokens per verify pass → amortizes the 381 GB/s decode kernel)

Mechanism common to all: a cheap drafter proposes k tokens; the target verifies them in **one** bandwidth-bound forward pass. If acceptance length is τ, decode tok/s ≈ τ × (verify-pass tok/s) − drafter overhead. On B70 the verify pass is exactly the EXL3 kernel that already runs at 381 GB/s, so every extra accepted token is nearly free bandwidth-wise; the binding constraints are (a) drafter sequential steps (instruction-issue and launch latency), (b) drafter weight traffic sharing the same card.

## 2. Prefill levers (moves: FLOPs/token and DPAS utilization)

### 2.1 Int8-activation GEMM: W4A8 / W8A8
- **SmoothQuant** (W8A8, arXiv 2211.10438, https://arxiv.org/abs/2211.10438): migrates quantization difficulty weights→activations; **1.56×** inference speedup (A100) with INT8 GEMMs, lossless-ish quality. Prereq: hardware INT8 matmul — **B70 has it (367 TOPS INT8 DPAS, datasheet)**.
- **QServe / QoQ (W4A8KV4)** (arXiv 2405.04532, https://arxiv.org/abs/2405.04532): key finding for B70 — naive INT4 dequant on GPU vector cores costs **20–90% runtime overhead**; QServe cuts it with progressive quantization + register-level parallelism: **1.2×** (Llama-3-8B, A100), **1.4×** (L40S), **2.4–3.5×** for Qwen1.5-72B vs TensorRT-LLM. That 20–90% overhead number is the same pathology the repo measured inside trellis decode kernels **(repo)**.
- **QQQ (W4A8)** (arXiv 2406.09904, https://arxiv.org/abs/2406.09904): per-group W4A8 GEMM **3.29×**, per-channel **3.67×** vs FP16 GEMM; end-to-end **2.24×** vs FP16, 2.10× vs W8A8, 1.25× vs W4A16 (NVIDIA A100/H100-class). Int8-activation GEMM is the single biggest published prefill multiplier.
- **Atom (W4A4)** (arXiv 2310.19102, https://arxiv.org/abs/2310.19102): mixed-precision 4-bit weight+activation; **up to 7.7×** throughput vs FP16 at high batch, 2.5× vs INT8 (A100, high-batch serving).
- **Quality risk on this repo**: W4A16 GPTQ/AutoRound on Qwen3.8-27B already failed the canary (30-defect arithmetic) **(repo)**; W4A8 failed quality once **(repo)**. W8A8 + SmoothQuant-style scaling is the safest int8-activation entry point; validate against the in-head-arithmetic canary before trusting any W4A8 claim.
- **B70 mapping**: prefill is compute-bound → INT8 DPAS gives ~2× FLOPs headroom vs FP16 (datasheet INT8 peak; FP16 ≈ half). The repo's OV int4 route and vLLM-XPU W8A16 FP8 route exist; a **W8A8 INT8-DPAS prefill path** (weights INT8, activations INT8) is untried **(repo)** — QQQ/QServe kernel recipes (fused dequant into DPAS operand setup, register-parallel unpack) transfer conceptually but need SYCL/oneDNN reimplementation [INFERENCE].

### 2.2 Chunked prefill + stall-free scheduling
- **Sarathi-Serve** (OSDI'24, arXiv 2403.02310, https://arxiv.org/abs/2403.02310): chunked prefill + piggybacked decode: **2.6×** serving capacity (Mistral-7B, 1×A100), up to **3.7×** (Yi-34B, 2×A100), **5.6×** with pipeline parallelism (Falcon-180B) vs vLLM. Mechanism: fixed-size prefill chunks mixed into decode batches → no decode stalls, near-full DPAS utilization, uniform iterations. No quality risk (pure scheduling). **B70**: vLLM-XPU supports chunked prefill **(repo runs vllm-xpu)** — tuning chunk size to fill 256 XMX engines is a config lever, not a research lever; biggest TTFT/goodput win available at zero quality risk.

### 2.3 Sparse / linear attention prefill
- **MInference 1.0** (arXiv 2407.02490, https://arxiv.org/abs/2407.02490; https://github.com/microsoft/MInference): dynamic sparse attention (A-shape, vertical-slash, block-sparse patterns); **up to 10× prefill latency reduction** on long prompts (A100), accuracy maintained, no retraining.
- **SeerAttention** (arXiv 2410.13276, https://arxiv.org/abs/2410.13276): learned block-level gate; ~5× attention FLOPs reduction with a 512-token gate blocksize in later versions [v4 reports 4–5×; exact factor per paper version].
- **NSA** (arXiv 2502.11089, https://arxiv.org/abs/2502.11089): natively *trained* hierarchical sparse attention; substantial 64k-sequence speedups in decode/forward/backward — requires the model trained with it (DeepSeek lineage).
- **B70 mapping**: attention at long prompt is quadratic FLOPs on FP16/INT8 DPAS; MInference-style sparsity is a drop-in kernel change (no retraining) and is the only member of this family usable on stock Qwen3.8. Repo already exploits the *architecture* route instead: Qwen3.8-Flash-Next hybrid/linear-attention MoE prefills 8K at **989 tok/s (repo, Strata SYCL)**.

### 2.4 Prefix caching
- vLLM Automatic Prefix Caching docs: https://docs.vllm.ai/en/stable/features/automatic_prefix_caching — reuses KV of shared prefixes; gains scale with hit rate (no fixed speedup number published; effect = skipping the FLOPs+bytes of cached tokens).
- **(repo)**: exl3xpu route already sees **5.4× cache** benefit on repeated-prefix tasks. Lever = maximize hit rate (stable system prompt, cache-aware routing across the two cards), not new tech.

### 2.5 Prompt compression
- **LLMLingua** (arXiv 2310.05736, https://arxiv.org/abs/2310.05736; https://github.com/microsoft/llmlingua): up to **20×** prompt compression with small quality loss (per repo/blog claims; paper reports up to 20× with negligible loss on some tasks, 2–5× typical). Moves FLOPs/token directly: prefill time ∝ prompt length. Quality risk is real (information deletion) — canary-gate it. Best paired with prefix caching for RAG-style repeated contexts.

### 2.6 Prefill on INT8 DPAS = 2× vs FP16 (B70-specific)
Mechanism: DPAS systolic array peak scales with operand width; B70's 367 TOPS is quoted at INT8 dense (datasheet above); FP16 XMX is half-rate per the same XMX family scaling (oneAPI XMX guide lists int8/fp16/bf16/tf32 as the XMX types, https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/xmx.html). Published evidence of the *system* value: QQQ's W4A8 GEMM 3.29–3.67× vs FP16 (§2.1). On B70 the equivalent path requires oneDNN/SYCL INT8 GEMM for prefill shapes; llama.cpp SYCL already has INT8 Q8_0 quantized KV/matmul paths **[UNVERIFIED for DPAS selection on BMG]**. Expected prefill gain if realized cleanly: ~1.7–2× **[INFERENCE]**, quality-gated.

## 3. KV cache (moves: bytes_per_token at long context, and KV capacity → batch/yield)

Decode bytes/token = weights/format + KV read per token. Per-token KV bytes on the 27B route ≈ pool-derived **~55 KB/token fp8 [INFERENCE from repo pool: fp8 KV pool 287,040 tokens]** → at 16K context, KV adds ~0.86 GB/token-pass vs ~13.5 GB EXL3 weights ≈ +6% traffic; at 64K+ or batched decode it becomes a first-order term.

- **FP8 KV**: only dtype available in exl3xpu today **(repo)**. Reference: QServe uses KV4 with SmoothAttention to make 4-bit KV safe (arXiv 2405.04532, §2.1 above); DeepSeek-V3 trains/serves with FP8 KV (arXiv 2412.19437, https://arxiv.org/abs/2412.19437). Halves KV bytes vs FP16 baseline; on B70 it's already the floor for that engine.
- **KIVI (2-bit asymmetric KV)** (arXiv 2402.02750, https://arxiv.org/abs/2402.02750; https://github.com/jy-yuan/KIVI): per-channel keys / per-token values, 2-bit + fp16 outliers: **2.6×** less peak memory, **4×** batch, **2.35–3.47×** throughput (Llama/Falcon/Mistral; NVIDIA GPUs). Gain is a *batching* effect: KV bytes/token halving alone gives ~2× KV-traffic reduction at equal accuracy risk (small, tuning-free per paper).
- **TurboQuant** (arXiv 2504.19874, https://arxiv.org/abs/2504.19874): random-rotation + optimal scalar quantizers, online/O(1): **absolute quality neutrality at 3.5 bits/channel, marginal at 2.5 bits** for KV cache. Third-party vLLM integrations exist (e.g. https://github.com/thepradip/turboquant-vllm) **[UNVERIFIED upstream/XPU status]**. On B70 the Hadamard-style rotation adds vector-engine instructions — the same wall as trellis decode — so budget kernel time, not just bytes [INFERENCE].
- **KV offload to host/SSD**: Mooncake (FAST'25 Best Paper, https://www.usenix.org/conference/fast25/presentation/qin): KV-centric disaggregated cache; **+59–498%** effective request capacity on long-context traces, production +115%/+107% requests on A800/H800. vLLM-Ascend documents the pattern (CPU offload of inactive blocks): https://docs.vllm.ai/projects/ascend/en/latest/user_guide/feature_guide/kv_cache_cpu_offload.html. **B70 note**: offload trades HBM capacity for PCIe trips; it moves *capacity/batch*, not decode bandwidth of resident tokens — helpful for the C16 aggregate route (426 tok/s, repo) and for cross-card prefill hand-off (§4).

## 4. Multi-GPU without atomics (two cards, copy-only 11–12 GB/s, no peer atomics — repo)

### 4.1 Prefill/decode disaggregation
- **DistServe** (OSDI'24, https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin): separate prefill vs decode GPU pools: **7.4×** more requests or **12.6×** tighter SLO vs colocated SOTA (A100/H100 clusters).
- **Splitwise** (ISCA'24, https://www.microsoft.com/en-us/research/wp-content/uploads/2023/12/Splitwise_ISCA24.pdf): phase-split machines with layer-wise async KV transfer: **1.4×** throughput at 20% lower cost, or **2.35×** under same power/cost (A100/H100, InfiniBand-class links). Its Insight VII (decode tolerates power caps ~50% with no latency change) matters for a 230 W-capped B70 rig.
- **B70 mapping [INFERENCE]**: card0 = prefill specialist (INT8 DPAS path, chunked), card1 = decode specialist (EXL3 4bpw + MTP3). KV hand-off per request at 8K ctx ≈ 8192 × ~55 KB ≈ **~450 MB → ~40 ms at 11.5 GB/s**, vs the 27B route's decode step time (~16 ms/token at 63 tok/s) — overlap it layer-by-layer Splitwise-style and it's ~0.5% of an 8K prefill (Strata route: 8K in ~8.3 s). Only copies cross the link — no atomics needed. This matches the repo's "two independent services" default but adds a router + KV copy.

### 4.2 Pipeline parallel (PP2)
Sarathi-Serve's best PP result: 5.6× capacity (Falcon-180B, 8 GPUs; arXiv 2403.02310 above). Bubble = (p−1)/(m+p−1) → with p=2 and chunked micro-batches m≥8 the bubble ≤11% **[INFERENCE]**; per-microbatch activation copy = hidden×tokens×2B (~few MB) — well inside 11–12 GB/s. **But (repo)**: pp2_status = blocked on current engines (exl3xpu/vllm-xpu plugin paths). Feasible only as a custom SYCL runner; expected decode gain over 2 independent services is nil for bs=1 (pipeline helps throughput, not single-stream latency) — rank below disaggregation.

### 4.3 Expert parallel for MoE
- **vLLM EP deployment** (https://docs.vllm.ai/en/stable/serving/expert_parallel_deployment/): attention replicated, experts sharded; needs per-layer token all-to-all.
- **DeepEP** (https://github.com/deepseek-ai/DeepEP): high-throughput/low-latency all-to-all kernels for MoE EP (NVLink/RDMA class fabric).
- **B70 mapping [INFERENCE]**: no atomics is survivable (all-to-all = copies), but per-layer dispatch latency over copy-only P2P (~tens of µs sync × 2 directions × ~90 MoE layers) risks eating the win; payloads per layer are small (tokens×hidden), so bandwidth is fine but latency/synchronization dominates at bs small. The repo's current answer — **expert streaming on one card (Strata SYCL, 48 tok/s decode)** — keeps experts in local VRAM instead; sharding experts across both cards halves per-card expert bytes → potential ~2× decode ceiling for the Flash-Next route **[INFERENCE]**, at the cost of layer-synchronous copies. Try after disaggregation.

### 4.4 Draft-on-other-card speculative decoding
- **SpecEdge** (arXiv 2505.17052, https://arxiv.org/abs/2505.17052): drafter on client GPU, target on server GPU, "exchanging only token outputs": **2.22× server throughput, 1.91× cost efficiency, −11.24% ITL** (edge+server, network link).
- **B70 mapping [INFERENCE]**: GPU0 hosts drafter (EAGLE-3 head or DFlash block-diffusion, ~1–2 GB), GPU1 hosts full EXL3 4bpw target. Per round the link carries only token IDs + accept mask (<1 KB) → copy latency ≪ 16 ms verify; drafting overlaps target verification continuously. Removes drafter weights/steps from the target card entirely — strictly better than same-card drafting where MTP3's sequential steps already tax launch latency. Caution from local skill/repo archive (`dflash-rpc-research` skill; `archive/dflash-investigation/`): speculative **rollback over a slow link** was the failure mode at 1 GbE; at 11–12 GB/s P2P the same economics flip positive, but verify-batch sizing and KV-rollback support in llama.cpp/exl3xpu remain the engineering risk (noted in skill conclusions).

### 4.5 Copy-engine collectives
llama.cpp RPC server (https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md) exposes remote devices; the repo measured captured copy-only collectives ≤60 µs for TP2-tensor class **(repo, RL-103..105)** but sharded loaders are absent — stock TP2 stays blocked. Realistic copy-collectives lever: layer-wise KV streaming (§4.1) and cross-card draft handoff (§4.4), not allreduce.

## 5. Weight formats beyond int4 (moves: bytes_per_token at decode; instruction cost per weight)

- **QTIP** (arXiv 2406.11235, https://arxiv.org/abs/2406.11235): trellis-coded quantization — stateful decoder separates codebook size from bitrate; SOTA at 2–3 bits, hardware-efficient bitshift lookup. Decode instruction cost is the design center (lookup-only vs compute codes).
- **EXL3 = streamlined QTIP** (turboderp: "EXL3 … is a streamlined variant of QTIP from Cornell RelaxML", https://github.com/turboderp-org/exllamav3) — already the repo's decode champion: 4bpw, verify 381 GB/s, decode wall = instruction issue **(repo)**. Lever direction: M=8 codes at lower bpw cut bytes/token but multiply integer instructions per weight → trades bandwidth (63% utilized) against issue rate (the wall). The kernel-side lever is *fewer instructions per trellis step* (bitshift/lookup-only codes), not more bits of quantization [INFERENCE from QServe's 20–90% dequant-overhead finding, arXiv 2405.04532].
- **AQLM** (arXiv 2401.06118, https://arxiv.org/abs/2401.06118): additive multi-codebook quantization, Pareto-optimal <3 bpw; ships fast GPU/CPU decode kernels that match/beat FP16 (NVIDIA). Codebook gather + FMA runs on vector engines — no codebook hardware on Xe2; expect EXL3-like instruction-bound behavior [INFERENCE]. GGUF/AQLM support in llama.cpp [UNVERIFIED current state].
- **HQQ** (https://github.com/dropbox/hqq; blog https://mobiusml.github.io/hqq_blog): calibration-free, minutes-fast quantization to 2/3/4/8-bit; quality competitive at 4-bit, usable at 2-bit with LoRA repair (paper/blog). Its value here is *iteration speed for format experiments*, plus no-calibration export for canary sweeps [no B70-native kernel claims].
- **Any-Precision LLM** (ICML'24, arXiv 2402.10517, https://arxiv.org/abs/2402.10517; https://github.com/SNU-ARC/any-precision-llm): one bit-flexible GPTQ ladder serves 3/4/5/6/8-bit from one artifact. Decode speed = GPTQ-class kernels (no trellis advantage); useful for quality-vs-bpw sweeps but B70 decode already has a better kernel family (EXL3).
- **2:4 structured sparsity**: SparseGPT (ICML'23, arXiv 2301.00774, https://arxiv.org/abs/2301.00774) prunes to 50% one-shot at minimal loss. The 2× *compute* speedup requires sparse tensor cores (NVIDIA Ampere+); Intel Xe2/oneDNN exposes no 2:4 sparse DPAS (XMX types list: https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/xmx.html) — so on B70 you'd pay index overhead for ~½ weight bytes without GEMM acceleration. **Low applicability** [INFERENCE].
- **INT4/INT2 XMX datapath**: third-party Xe2 analysis reports XMX supports INT4/INT2 matmul (https://www.hwcooling.net/en/batttlemage-details-of-intel-xe2-gpu-architecture-analysis) — if exposed via oneDNN/SYCL, W4A4 (Atom-style, arXiv 2310.19102) could exceed the INT8 367 TOPS peak for prefill **[UNVERIFIED software exposure on BMG]**.

## 6. Ranking — top 8 levers for B70 by (expected end-to-end gain × feasibility)

### Decode (baseline: 63.25 tok/s @230W, MTP3, EXL3 4bpw; C16 aggregate 426 tok/s)
1. **DFlash-style single-pass drafter for the 27B route** — proven repo-side on Nemotron (186.6 tok/s, n7) and 2.5× over EAGLE-3 in paper; replaces depth-recursion MTP3 steps that hit the launch/issue wall. Gain est. +30–60% [INFERENCE]; feasibility: drafter port to exl3xpu is the gate.
2. **Drafter-on-GPU0 / target-on-GPU1 (SpecEdge pattern)** — 2.22× server throughput published; link needs <1 KB/round; removes drafter traffic from target card. Feasibility: high (router + rollback support), no atomics needed.
3. **Suffix/n-gram lookup stacked under MTP/DFlash for agentic loads** — 2.4–5.3× published on copy-heavy tasks; zero GPU drafter cost; trivial to try behind a workload classifier.
4. **EAGLE-3 head for Qwen3.8 (if trained)** — 6.5× published, 1.15× over by PARD; feasibility gated on head training + SGLang-class verify kernel in exl3xpu.
5. **KV quantization below fp8 (KIVI 2-bit / TurboQuant 3.5-bit) for long-context + C16 batch** — 2.35–3.47× throughput published (batch effect); B70 benefit grows with context length and concurrency; gate: extra vector-engine instructions for rotation/dequant.
6. **MoE expert sharding/streaming across both cards (Flash-Next route)** — halves expert bytes → ~2× decode ceiling [INFERENCE]; gated by layer-sync copy latency (no atomics needed, just copies).
7. **Power/thermal headroom to 230W+ and kernel-level instruction-diet for trellis decode** — repo already measured +24.7–28.7% 150→230W; further yield gains come from lookup-only trellis codes (QTIP design space).
8. **Any-precision ladder for per-task bpw (4→3.5bpw on easy tasks)** — bytes/token −12% with quality-gated routing; modest, cheap.

### Prefill (baseline: 8K @ 989 tok/s Strata Flash-Next; OV/vLLM routes slower)
1. **Chunked prefill + stall-free scheduling tuning (Sarathi-style)** — 2.6–3.7× capacity published; pure config/scheduler work in vLLM-XPU; zero quality risk.
2. **Prefix-cache-aware routing across the two cards** — repo already banks 5.4× cache; routing/hit-rate engineering is free FLOPs.
3. **W8A8 INT8-DPAS prefill GEMM path (SmoothQuant-recipe)** — 1.56× published for W8A8, up to 2.24× end-to-end (QQQ) on NVIDIA; B70 has the 367-TOPS int8 array; needs SYCL/oneDNN kernel work + canary gate (W4A8 burned us once — repo).
4. **MInference-style dynamic sparse attention for long prompts** — up to 10× prefill latency published (A100, ≥32K prompts); drop-in, no retraining; value concentrated in long-context cells (p8192+).
5. **Prefill/decode disaggregation across the two cards (DistServe/Splitwise)** — 7.4× goodput published (cluster-level); B70 version = card0 prefill / card1 decode + ~40 ms/8K-req KV copy; big TTFT + goodput win at high load.
6. **Prompt compression (LLMLingua) for RAG-heavy traffic** — up to 20× token reduction published; quality-risk (canary-gate); interacts with suffix decoding (compressed prompts raise n-gram mismatch — test jointly).
7. **Hybrid/linear-attention model routing (Flash-Next class)** — repo already at 989 tok/s; expanding hybrid coverage (more models/servables) is the architectural prefill lever.
8. **W4A4 / INT4-XMX prefill experiment** — Atom published 7.7× vs FP16 (high batch, NVIDIA); B70 XMX INT4/INT2 support reported at ISA level [UNVERIFIED software exposure] — research-grade.
