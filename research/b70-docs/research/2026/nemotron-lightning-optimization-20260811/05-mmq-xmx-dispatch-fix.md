# 05 — MMQ/XMX Dispatch Fix: The `__dp4a` Scalar Emulation Discovery

## The discovery

While profiling why Nemotron's GEMV achieves only 11% bandwidth efficiency (vs Qwen's 36%),
I traced the dispatch chain in `ggml/src/ggml-sycl/ggml-sycl.cpp`:

```
1. F16 permuted p021  → special path (skip)
2. F16 permuted nc     → special path (skip)
3. F16 batched         → special path (skip)
4. DMMV                → disabled when MMVQ available
5. MMVQ                → SELECTED for Q4_K M=1  ← THIS RUNS
6. MMQ (XMX/DPAS)      → never reached
7. fallback            → never reached
```

The **MMVQ** kernel was selected for all Q4_K decode GEMVs. MMVQ uses `vec_dot_q4_K_q8_1`
which calls `__dp4a` for INT8 dot products.

## The `__dp4a` emulation

In `ggml/src/ggml-sycl/dpct/helper.hpp:1859`:

```cpp
template <typename T1, typename T2, typename T3>
inline auto dp4a(T1 a, T2 b, T3 c) {
    dot_product_acc_t<T1, T2> res = c;
    auto va = extract_and_sign_or_zero_extend4(a);
    auto vb = extract_and_sign_or_zero_extend4(b);
    res += va[0] * vb[0];
    res += va[1] * vb[1];
    res += va[2] * vb[2];
    res += va[3] * vb[3];
    return res;
}
```

This is a **scalar emulation** of NVIDIA's `__dp4a` intrinsic (4 INT8 multiply-accumulates).
It was auto-generated by Intel's DPC++ Compatibility Tool (dpct) when porting from CUDA.

On the B70's Xe2 architecture:
- **256 XMX engines** can do INT8 matrix multiplies via DPAS — **completely idle**
- **Scalar ALUs** do 4 sequential integer multiplies — slow, poor throughput
- The Xe2 DPAS instruction can do `8×16 × 16×16` INT8 matrix multiply per clock per XMX engine

## The fix

In `ggml/src/ggml-sycl/ggml-sycl.cpp`, after the `use_mul_mat_q` and `use_mul_mat_vec_q`
computation, add:

```cpp
#ifdef SYCL_USE_XMX
    // On Intel Xe2, MMVQ uses scalar dp4a emulation (4 scalar INT8 MULs)
    // while MMQ uses XMX/DPAS hardware. Prefer MMQ when XMX is available.
    if (use_mul_mat_q) {
        use_mul_mat_vec_q = false;
    }
#endif
```

This makes the dispatch fall through to step 6 (MMQ) instead of step 5 (MMVQ),
using the XMX-accelerated path for Q4_K (and all other K-quants).

## Result

| Path | tg128 (t/s) | Notes |
|------|------------|-------|
| MMVQ (scalar dp4a) — original | 36.83 ± 0.03 | 256 XMX engines idle |
| MMQ (XMX/DPAS) — fixed | 38.18 ± 0.08 | XMX active, +3.7% |
| DMMV (dequant→F32 GEMV) | timeout (>5× slower) | F32 dequantization overhead |

## Why the improvement is modest (+3.7%, not 10×)

GEMV at M=1 is **memory-bound**, not compute-bound. The kernel spends most of its time
reading weight data from GDDR6, not doing multiply-accumulates. Whether the MACs are done
by XMX or scalar ALU doesn't matter much when the kernel is waiting for memory.

The XMX speedup helps the compute portion but the memory access pattern remains the bottleneck.
To get a larger improvement, the **memory access pattern** needs to be optimized (better
coalescing, larger reads, reduced L2 pressure).

## Applicability to other models

This fix applies to ALL K-quant models (Q4_K, Q5_K, Q6_K, Q4_K_M, etc.) on Xe2 GPUs.
It should also improve Qwen MoE and other models. Needs verification that MMQ doesn't
regress for non-Nemotron models.

**Risk:** MMQ might be slower than MMVQ for some quant types or matrix sizes.
The `SYCL_USE_XMX` guard limits the change to Xe2+ hardware only.
