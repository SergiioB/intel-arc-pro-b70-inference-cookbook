## Root Cause Analysis

### Most Likely: Auto-Suspend Timer
The `ai-node-sleep.timer` is configured to suspend at **01:00 Europe/Madrid** daily. However, system logs show this was at ~22:15-22:20, suggesting:
- Timer fired early due to timezone drift
- Or there's another suspend mechanism (laptop lid close simulation, etc.)

### Alternative Causes
1. **Filesystem check (fsck):** Running on large disk, blocking boot
2. **Service dependency deadlock:** llama-profile.service hanging on model load
3. **Network service timeout:** Waiting for something that never arrived

### Supporting Evidence
- Ping works (kernel alive)
- SSH banner times out (userspace not ready)
- No HTTP response (inference service dead)
- Timeline matches typical suspend → wake → boot stall pattern

### If It's fsck Running
- Wait for completion (may take 30-90 min for 1TB+ disks)
- Do not interrupt
- After completion, verify filesystem health with `fsck -n /dev/sdX`

### If It's a Service Hang
- Stop llama-profile.service: `systemctl --user stop llama-profile.service`
- Kill stuck processes: `killall llama-server`
- Restart cleanly: `systemctl --user restart llama-profile.service`

### If It's a Kernel Panic
- Check crash logs: `dmesg | grep -i panic`
- Review recent kernel updates: `dpkg -l | grep linux-image`
- Consider kernel downgrade if issue persists

## Lessons Learned

1. **Remote benchmarking requires monitoring:** Should have used `notify_on_complete=true` and background jobs
2. **Sleep timers are dangerous during remote work:** Should have been disabled before starting
3. **WoL only works from suspend, not shutdown:** System may have gone to full shutdown instead of suspend
4. **SSH timeout during benchmarks:** Should have checked session health before launching long-running jobs
5. **No remote hard reset capability:** Need to consider smart plug or BMC for future
